# ORIGEN v0.3 — External Trust Provider Conformance Profile v1

**Status:** RESEARCH / IMPLEMENTATION GATE. This profile is not a provider implementation, trust anchor, or production authorization.

## Purpose

Turn the `DeploymentTrustProvider` protocol into an acceptance contract for an independently operated provider. The application-side protocol and synthetic tests are necessary but insufficient: a Python object implementing the protocol is not evidence of institutional trust, durable anti-rollback, or independent custody.

The provider MUST be a separately deployed security boundary. It MUST NOT be loaded from request data, repository contents, environment variables controlled by the submitter, CI secrets, or a caller-selected Python module.

## Security boundary

The deployment must identify and independently control all of the following:

1. **Trust-anchor ceremony:** root Ed25519 public key, key ID, generation, authorized custodians, approval quorum, activation time, and revocation/rotation procedure. Record the ceremony evidence and exact key fingerprint. A key generated by the application or supplied with a receipt is not a trust anchor.
2. **Provider identity:** authenticated workload identity and mutually authenticated transport. The caller must authenticate the provider; the provider must authorize the caller and fixed `CLASSIC` domain.
3. **Durable monotonic state:** policy sequence/digest, trusted-time upper watermark, physical-context generation/digest, ledger checkpoint, witness-registry sequence/digest, and consumed nonce challenges. State must be transactionally coupled.
4. **Independent clock:** separately provisioned clock verification key, authenticated source, bounded uncertainty, signed freshness lease, replay protection, and authoritative lease validation at commit.
5. **External evidence verification:** exact bytes for receipt, policy, custody record, portfolio, detached signatures, both RFC 3161 tokens, manifest, ledger entry, inclusion and consistency proofs, signed checkpoints, witness registry, and every witness statement. Verification uses provider-owned roots, revocation state, trusted time, and quorum policy.
6. **Operational controls:** dual control for trust changes, immutable audit export, alerting on rollback/equivocation, backup/restore controls, and an independently held recovery procedure.

A digest of a provisioning record is only a consistency reference. It does not authenticate the record or the ceremony.

## Required transaction

A provider implementation MUST execute this as one linearizable operation:

- Authenticate caller, provider instance, policy domain, and request size limits.
- Read authoritative state and compare the exact expected generation and all expected state digests.
- Resolve root, clock, custodian, log, registry, and witness keys from provider-owned trust configuration.
- Verify all supplied exact bytes and all identity, signature, revocation, time, quorum, and continuity constraints.
- Verify that the old checkpoint equals the persisted checkpoint; verify the new checkpoint's signed continuity proof; reject tree-size rollback and same-size equivocation.
- Verify registry sequence monotonicity and reject same-sequence/different-digest equivocation.
- Verify challenge freshness and atomically consume challenge and nonce.
- Recompute the trust-configuration and clock-sample digests from authoritative provider state; never trust caller-computed digests.
- Atomically persist the accepted policy/time/evidence watermarks and increment the state generation exactly once.
- Return a commit receipt binding the exact candidate digests, prior and resulting generation, outcome, and resulting watermarks.

If any verification, durable write, response construction, or commit certainty fails, the provider MUST fail closed. An ambiguous commit outcome MUST be resolved by reading authoritative state; it must never be retried as a fresh advance without reconciliation.

## Mandatory adversarial conformance tests

The integration suite MUST run against the actual deployed provider and a separately authenticated verifier. Synthetic unit tests do not satisfy this gate.

| Test | Required result |
|---|---|
| Restore an old database snapshot after a successful advance | Provider detects rollback using an independently protected monotonic anchor, or refuses service |
| Replace root key while retaining key ID/generation | Reject configuration drift |
| Replace clock key/sample between snapshot and CAS | Reject; no state advances |
| Race two valid advances from the same generation | At most one commits; the other receives conflict |
| Replay consumed timestamp challenge or nonce | Reject |
| Submit same policy sequence with another envelope digest | Reject equivocation |
| Submit older policy, checkpoint, or registry sequence | Reject rollback |
| Submit same-size checkpoint with another root or checkpoint digest | Reject equivocation |
| Change any single byte in every evidence artifact class | Reject the altered artifact |
| Remove one witness or duplicate a witness identity | Reject unless the independently provisioned quorum policy explicitly permits it |
| Expire/revoke signer or TSA certificate at the relevant verification time | Reject |
| Disconnect provider during commit | Fail closed and reconcile exact durable state before retry |
| Restore backup into a second provider instance | Detect split-brain or require an independently authorized recovery transition |
| Change caller identity or request domain | Reject authorization/domain mismatch |

For every negative test, assert both the error class and that **none** of the policy, time, nonce, physical-context, ledger, registry, or custody watermarks advanced.

## Evidence required for acceptance

The deployment owner must produce, without exposing private keys:

- signed trust-anchor ceremony record and independently verified public-key fingerprint;
- provider image/build provenance and deployment identity;
- database transaction/isolation evidence and storage anti-rollback design;
- signed clock-source policy and sample-verification evidence;
- certificate-chain and revocation validation report for each external signer/TSA;
- provider conformance test report tied to the deployed image digest;
- audit-log export and independent verification instructions;
- backup/restore and disaster-recovery test results;
- independent reviewer sign-off and named operational ownership.

Every report must identify its exact software/image digest, test inputs, execution time, verifier version, and result. Screenshots, prose assertions, and CI status alone are not evidence of provider conformance.

## Promotion gates

The following are separate gates and MUST NOT be conflated:

- **Application contract:** code and synthetic tests pass.
- **Provider conformance:** independently deployed provider passes this profile.
- **Physical provenance:** official draw records, custody, and independent source evidence are authenticated.
- **Predictive evidence:** at least 100 prospective *Chispazo Clásico* draws are sealed before close and evaluated under the preregistered protocol; positive lift, Holm-adjusted (p < 0.05), and anytime e-value (ge 20) are all required.
- **Operational authorization:** independent reviewers authorize a named deployment and scope.

Until every applicable gate is satisfied, the only valid status is:

`BLOCKED / RESEARCH_ONLY_NO_EDGE`

No provider implementation, key ceremony, institutional evidence, prospective performance, or production authorization is claimed by this document.
